Agent Capability Exchange

Abstract. ACX is a vendor-neutral semantic contract for discovering, evaluating and invoking capabilities in an agent-native economy. It is transport-neutral and composes with existing execution, identity, authorization and payment protocols.

1. Scope

ACX standardizes capability description, discovery, preflight, commitment, evidence, recovery and conformance. It does not define model inference, agent reasoning, a new payment rail, or a replacement for MCP, A2A, HTTP or gRPC.

2. Core requirements

Providers MUST distinguish observational actions from consequential actions; MUST expose externally visible side effects; MUST declare authorization requirements; MUST provide deterministic input/output schemas; and SHOULD provide verifiable execution evidence. Irreversible actions MUST explicitly declare irreversibility.

3. Discovery and manifest

Public providers SHOULD expose https://{domain}/.well-known/acx.json. The document contains provider identity, supported ACX versions, trust material, capability records and optional registry metadata.

{
 "acx":"0.1",
 "provider":{"id":"urn:acx:example:lab","name":"Example Laboratory"},
 "capabilities":[{
   "id":"lab.run_assay","version":"1.2.0",
   "inputSchema":{"$ref":"https://example.org/assay-input.json"},
   "outputSchema":{"$ref":"https://example.org/assay-output.json"},
   "bindings":[{"type":"mcp","server":"https://example.org/mcp","tool":"run_assay"}],
   "effects":["consumes-material"],"risk":"consequential",
   "authority":{"scopes":["lab:execute"],"approval":"human"},
   "economics":{"model":"quote","currency":"USD"},
   "evidence":{"receipt":"signed"},"recovery":{"reversible":false}
 }]}

4. Capability record

FieldMeaning
id, versionStable semantic identity and compatibility.
inputSchema / outputSchemaDeterministic machine-readable contracts.
bindings[]MCP, A2A, HTTPS, gRPC or future execution bindings.
authorityScopes, delegation and approval requirements.
effects[]External mutations: money, publication, physical motion, resource consumption, deletion.
economicsPricing, quotation, metering and compatible settlement mechanisms.
evidenceReceipts, signatures, artifacts and verification rules.
recoveryCancellation window, compensation action and reversibility.

5. Lifecycle

  1. DISCOVER — retrieve a manifest directly or through a registry.
  2. PREFLIGHT — validate schema, authority, price ceiling, effects, risk and policy.
  3. QUOTE — when needed, obtain a time-bounded signed quote.
  4. AUTHORIZE — obtain delegated authority and any required human approval.
  5. COMMIT — create an idempotent commitment identifier before consequential execution.
  6. EXECUTE — invoke the selected protocol binding.
  7. VERIFY — validate output and signed evidence.
  8. SETTLE — use the declared settlement mechanism where applicable.
  9. RECOVER — cancel, compensate or escalate using declared recovery semantics.

6. Risk classes

R0 observational: no external mutation. R1 reversible: mutation with deterministic rollback. R2 consequential: financial, public, privacy-sensitive or resource-consuming action. R3 physical/safety critical: actions capable of affecting people, physical assets or regulated systems. Providers MAY define stricter domain profiles.

7. Security model

ACX assumes agent outputs can be wrong or adversarial. Consequential decisions MUST NOT depend on natural-language interpretation alone. Providers SHOULD use signed manifests, short-lived credentials, least-privilege scopes, idempotency keys, explicit amount/resource ceilings, replay protection and tamper-evident receipts. R3 profiles SHOULD require deterministic policy gates outside the generative model.

8. Interoperability

ACX bindings are adapters, not replacements. An MCP binding identifies a server/tool; an A2A binding identifies an Agent Card/skill; an HTTPS binding identifies an endpoint and method. Identity and authorization may reference OAuth/OIDC. Attestations may use W3C Verifiable Credentials. Commerce profiles may reference AP2-compatible mandates and receipts.

9. Versioning

The core uses semantic compatibility rules. Unknown optional fields MUST be ignored. Unknown mandatory extensions MUST cause preflight failure. Capability versions are independent of ACX core versions.

10. Conformance

The project should publish machine-readable JSON Schemas, a validator, test vectors and four badges: ACX Manifest, ACX Provider, ACX Client and ACX Registry. A conformance claim is valid only against a named test-suite release.

11. Governance

The intended governance is open, vendor-neutral and royalty-free. Specification changes use public proposals, review windows and interoperability evidence. No single model vendor, cloud provider, payment network or registry operator should control the core standard.

12. Initial extension profiles

Recommended first profiles: Commerce, Software & Cloud, Content & Publishing, Scientific Instruments, Manufacturing & Print, and Robotics. Each profile specializes effects, evidence and recovery without changing the core lifecycle.
